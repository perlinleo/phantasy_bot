# Закрытый Telegram-бот с плагинами обработки медиа

## 1. Назначение документа

Это техническое задание и последовательный план для coding agent в новом GitHub-репозитории. Реализовать работающий продукт небольшими проверяемыми этапами. Весь прикладной код — Python, весь проект — один репозиторий, один Docker image. YAML, Dockerfile, SQL и ресурсы допустимы. FFmpeg — внешняя системная зависимость. Автодеплой подготовить архитектурно, но подключать отдельным этапом после ручного запуска.

Продукт: личный закрытый Telegram-бот для владельца и вручную одобренных пользователей. Пользователь выбирает инструмент, отправляет входные данные, настраивает параметры, запускает обработку, видит прогресс и получает результат. Новые инструменты добавляются как доверенные Python-модули внутри репозитория.

Первые инструменты:

1. `text_card`: текст в красивую картинку — минимальный вертикальный сценарий и основа типографики.
2. `text_to_emoji`: целая надпись → квадратные плитки → пользовательский набор эмодзи → собранное сообщение.
3. `space_crawl`: жёлтый текст, уходящий вдаль на фоне звёзд, MP4 без звука для отправки анимацией.

Не включать в первую версию: оплату, публичную регистрацию, веб-панель, Mini App, inline-режим, группы и каналы, LLM, произвольные URL, горячую установку плагинов, сторонний marketplace, Kubernetes, Redis, Celery, распределённый execution engine. Доступ только в личной переписке с ботом. Сам аккаунт бота может быть найден любым человеком; закрытым является доступ к его функциям.

## 2. Зафиксированные решения

| Область | Решение |
|---|---|
| Python | 3.12 как консервативная стартовая версия; зафиксировать в проекте и image |
| Telegram | aiogram 3, long polling, один bot process |
| Схемы | Pydantic 2; строгие типы входа, настроек и результатов |
| Dependencies | uv, pyproject.toml, закоммиченный uv.lock |
| База | SQLite, WAL, foreign_keys=ON, busy_timeout; SQLAlchemy 2 + Alembic |
| DB concurrency | Короткие транзакции, async access через aiosqlite; никогда не держать транзакцию во время рендера или HTTP |
| Очередь | Таблица jobs в SQLite; polling воркера, атомарный claim |
| Runtime | Один image, два Compose services: bot и worker; отдельная one-shot команда migrate |
| Обработка | Один job runner subprocess на тяжёлую задачу, concurrency=1 по умолчанию |
| Рендер | Pillow для статической типографики; NumPy/Pillow + FFmpeg для видео |
| Файлы | Общий постоянный локальный volume /data |
| Проверки | pytest, ruff, mypy; короткие реальные media integration tests |
| UI | Русский; все время в БД UTC; timezone отображения конфигурируется |

Точные версии зависимостей агент выбирает совместимыми при создании проекта, проверяет по официальной документации и фиксирует lockfile. Не выдумывать существование API по этому документу. Не добавлять абстракции «на будущее» без конкретного использования.

SQLite volume должен находиться на локальной файловой системе одного хоста, не NFS/SMB. Один bot и один worker. Два сервиса используют один образ и одну БД. Масштабирование на несколько хостов потребует отдельного решения с PostgreSQL/очередью и здесь не реализуется.

## 3. Границы модулей

### domain

Типы Job, Progress, Artifact, AccessDecision, ошибки и допустимые переходы состояний. Не импортирует aiogram, SQLAlchemy, Pillow. Использование Pydantic для DTO допустимо.

### application

Сценарии: запрос доступа, approve/revoke, подготовка и подтверждение задачи, отмена, повтор, доставка, очистка. Работает через конкретные небольшие интерфейсы репозиториев/сервисов, только где есть реальная граница. Все entry points повторно проверяют доступ и принадлежность задачи.

### adapters/telegram

aiogram routers, клавиатуры, диалоги, преобразование Telegram-входа в наши DTO, представление прогресса, доставка. Не содержит рендеринг и бизнес-алгоритмы. Bot token доступен только этому процессу и migration не нужен.

### infrastructure

SQLite repositories, очередь, filesystem, subprocess runner, JSON logs, конфигурация. Telegram publication — инфраструктурный адаптер, который вызывается bot process на этапе delivery.

### plugins

Доверенные преобразователи входа. Не импортируют aiogram/SQLAlchemy, не отправляют сообщения, не создают Telegram-паки, не изменяют ACL, не обращаются напрямую к таблицам задач. Получают DTO, ресурсы и JobContext; создают локальные артефакты. Общие renderer/services живут отдельно и используются несколькими плагинами.

## 5. Контракт плагина

PluginSpec содержит:

- `id`: неизменяемое имя, например `text_to_emoji`.
- `version`: версия алгоритма/ресурсов для воспроизводимости и кэша.
- `contract_version`: версия общего протокола плагина, сначала 1.
- `title`, `description`.
- `input_model`, `options_model`: Pydantic-модели.
- `form`: явные описания полей и подписей для Telegram UI.
- `result_kinds`: поддерживаемые типы результата.
- `timeout_seconds`, `max_input_bytes` и ограничения конкретного входа.

Метод: `async run(input, options, context) -> PluginResult`. Форма typing может быть Generic/Protocol; агент обеспечивает проверку типов, не засоряя код Any.

JobContext предоставляет job_id, attempt_id, рабочую папку текущей попытки, scoped logger, типографику/FFmpeg, `report(stage, fraction=None)` и `check_cancelled()`. Fraction только при измеряемой доле текущего этапа. При отсутствии измерения UI показывает этап, а не придумывает процент и ETA.

Результат — tagged union JSON DTO: `ImageResult`, `AnimationResult`, `FileResult`, `EmojiCompositionResult`. Все пути относительны к workspace, при получении родитель проверяет containment, существование, формат, размер и запрещает выход через symlink. Не использовать pickle.

EmojiCompositionResult: tiles с local artifact ID и порядком, rows/columns или явное расположение, исходный текст для подписи/доступности, preview. Telegram IDs не входят в renderer output.

Плагин регистрируется явно в `plugins/registry.py`. На старте проверяются уникальность id, contract_version, схемы, допустимые поля и наличие delivery handler. Ошибка включённого плагина должна диагностироваться до polling. Отключённый плагин не показывается в меню.

Добавление обычного плагина: папка, spec, run, assets/licenses, запись в registry, contract/integration test. Новый тип взаимодействия или результата требует осознанного расширения SDK/UI/delivery. Не обещать поддержку произвольных диалогов автоматически.

Плагины исполняются как доверенный код репозитория. Процессная изоляция защищает отзывчивость и позволяет остановить рендер, но не является sandbox для недоверенного кода.

## 6. Диалоги и ввод

### 6.1. Пользовательский каталог и понятные названия

Технический `plugin_id` служит идентификатором протокола, а не основным названием в интерфейсе. Не показывать пользователю `space_crawl` или `text_card` вместо понятного названия. Стартовые названия: «Текстовая открытка», «Космические титры», «Надпись из эмодзи». Описания сообщают, что именно получится: PNG-картинка, MP4 без звука или композиция custom emoji. Для emoji честно различать реализованный PNG fallback и доступную публикацию custom emoji; не обещать второй результат при наличии только первого.

Каждый инструмент имеет карточку с названием, кратким описанием, заранее подготовленным примером результата и кнопкой «Использовать». Превью инструмента — лицензированный ресурс репозитория, не результат пользовательского рендера; просмотр каталога не создаёт job. Статические примеры отправлять как изображение, видеоэффекты — как короткую animation с caption. Кэш Telegram file_id допустим с привязкой к bot identity и версии ресурса. Если превью недоступно, показывать текстовую карточку без ложного заявления о наличии примера.

Расширить PluginSpec конкретно используемыми metadata: категория, поисковые теги и описание preview resource. Проверять ресурсы и metadata при plugins validate. Не создавать сотню пустых категорий или абстрактную поисковую платформу.

Каталог должен оставаться пригодным при 100 инструментах. Основные способы поиска — категории и поиск по названию, описанию и тегам, а не последовательное пролистывание всех инструментов. Добавить недавние инструменты и избранное; хранить их отдельно от пользовательского текста. SQLite/обычный поиск по metadata достаточен для этого масштаба, внешний поисковый сервис не нужен. Пагинация вспомогательная: короткие страницы результатов, навигация назад и возврат в каталог. Ни одно сообщение не содержит 100 кнопок. Начать с работающих поиска/категорий для имеющихся трёх инструментов; недавние и избранное добавить на этапе E.

`/tools` открывает каталог, `/new` — выбор инструмента или продолжение выбора через каталог. `/new PLUGIN_ID` остаётся необязательным shortcut, а не единственным понятным способом начать. Ввод номера вроде «2» не считать выбором инструмента без явного соответствующего режима. Неизвестные slash-команды не сохранять как текст draft; отвечать справкой, не менять draft/revision. Все переходы каталога и форм проверяют private chat, ACL, владельца draft и актуальность callback.

### 6.2. Настройки и содержательное подтверждение

После выбора инструмент показывает defaults и позволяет изменить поддерживаемые настройки. Сначала пресеты и небольшое число полезных параметров, дополнительные настройки раскрываются отдельно. Не требовать заполнить длинную анкету при каждом запуске. Для открытки: лицензированный шрифт/стиль, фон и цвет текста; для emoji: цвет/фон и читаемый layout в пределах лимитов; для титров: длительность и ограниченная скорость, остальные параметры только если реально реализованы renderer'ом. Недоступных переключателей и настроек-заглушек не показывать.

FormSpec описывает поля input и options явно. Options валидируются Pydantic, сохраняются в draft, показываются в summary, копируются в job и передаются runner'у. Нельзя сохранять пользовательский выбор в UI, а при рендере молча использовать defaults. Изменение текста или options увеличивает revision и инвалидирует прежнюю кнопку подтверждения. Unicode и переводы строк сохраняются без автоматического переписывания текста.

Экран подтверждения содержит понятное название инструмента, выбранный пользовательский ввод, текущие настройки и тип результата. Длинный ввод показывать безопасно усечённым с обозначением усечения и действием просмотра полного текста; исходный ввод не изменять. HTML экранировать на границе представления. Действия: «Создать», «Изменить текст», «Настройки», «Отменить». Пример инструмента не выдавать за персональное превью. Персональный preview — отдельная ограниченная операция только при наличии конкретной реализации; не выполнять тяжёлый рендер синхронно в handler.

### 6.3. Основные правила диалога

Не генерировать весь UI из произвольного JSON Schema. Поддержать небольшой FormSpec: text, choice, integer, boolean; image/file добавить при первом реальном плагине, которому это нужно. Для text сохранять переводы строк и Unicode, ограничивать длину и размер; экранировать отдельно на границе Telegram HTML. Текст никогда не используется как shell command, путь или произвольный FFmpeg filter expression.

Диалог: выбор инструмента → ввод → настройки с разумными defaults → сводка и кнопка «Создать» → задача. Один редактируемый draft на пользователя, несколько завершённых задач. Новая команда /new не отменяет уже запущенную задачу. /cancel отменяет текущий draft; отмена job — отдельной кнопкой или /cancel_job ID.

Draft в SQLite с revision, plugin_version, expires_at. Кнопки несут короткий opaque ID и revision; все значения сверяются на сервере. Старые кнопки отвечают «Этот шаг уже завершён». Повторное подтверждение не создаёт вторую задачу: уникальный submission key по draft_id/revision, создание job и фиксация подтверждения в одной транзакции. Update ID — дополнительная дедупликация; он не заменяет ключ операции.

Draft хранит input_json и options_json, а не только единственное поле text. Режим диалога (выбор, ввод, настройки, подтверждение) сохраняется явно. `/cancel` действительно закрывает draft; справка не сообщает, что уже работающий сценарий «будет добавлен позже». `/help` и сообщения меню соответствуют реализованным возможностям.

Обработчики updates короткие, без рендера и долгих сетевых вызовов. Для первой версии aiogram polling выполнять последовательно (handle_as_tasks=False), чтобы не подтверждать updates раньше завершения короткого сохранения. Файловые скачивания, публикация и доставка — фоновые задачи, отражённые в БД. Не заявлять exactly-once reception; ключевые действия идемпотентны, предусмотрены повторы пользователя.

Хранить drafts явно, не полагаться на MemoryStorage для важного состояния. Не делать вторую конкурирующую FSM поверх aiogram FSM без необходимости.

Команды: /start, /tools, /new, /jobs, /cancel, /help. Админ: /requests, /allow ID, /revoke ID, /users, /status. Длинные списки пагинируются. Не показывать чужие job/result даже при угаданном ID.

## 7. Доступ

OWNER_TELEGRAM_ID — обязательный числовой ID из конфигурации, всегда имеет доступ. Username — только справочная подпись. Telegram IDs хранить как 64-bit integer. Пользователь не может одобрить себя через callback, прислать чужой user_id или получить права владельца из БД.

Неодобренный пользователь может увидеть краткое описание и нажать «Запросить доступ». Заявка одна активная на ID; уведомление владельцу с approve/reject. Ограничить повторные заявки и уведомления cooldown. Owner должен сначала открыть бота; неполученное уведомление не уничтожает заявку, она видна в /requests.

Approve/revoke идемпотентны и пишутся в audit log. Revoke: закрыть draft, отменить queued jobs, запросить отмену running jobs, запретить последующую delivery. Повторно проверить ACL перед claim и перед отправкой. Уже отправленные сообщения или начатый HTTP request нельзя гарантированно отозвать; бот не обещает удаление ранее полученного контента.

## 8. Модель задач и восстановление

Статусы обработки: queued, running, completed, failed, cancelled, interrupted. `completed` означает, что локальный результат проверен и сохранён, а не обязательно доставлен. Доставка живёт отдельно: pending, sending, sent, failed, uncertain, suppressed. UI различает «обработано» и «отправлено».

Jobs: id UUID, user_id/chat_id, plugin_id/version/contract_version, input_json, options_json, status, stage/fraction, attempt_count, cancel_requested, created/started/finished_at, lease_owner/token/expires_at, heartbeat_at, result_manifest, error_code/safe_message. Не хранить secret credentials в JSON.

Очередь: атомарный claim в короткой SQLite write transaction. Только один runner одновременно по умолчанию. Claim задаёт lease и случайный fencing token. Heartbeat обновляет lease (пример: каждые 5 секунд, lease 30 секунд). Все изменения от попытки принимаются только с текущим token, чтобы устаревший runner не переписал результат.

Worker запускает subprocess `python -m media_bot run-job ...`. Вход и результат — JSON-файлы; события прогресса — bounded JSONL stdout, логи — stderr. Обязательно постоянно дренировать обе трубы, чтобы процесс не завис. Subprocess не имеет Telegram token; минимальный env. CPU-работа выполняется там, event loop бота и supervisor остаются отзывчивыми.

Timeout/отмена: выставить флаг, дать краткий grace period, затем остановить process group SIGTERM и SIGKILL при необходимости, включая FFmpeg children. Закрыть stdin/pipe, дождаться процесса, не оставлять сирот. SIGKILL/OOM могут не оставить диагностик: exit code тоже учитывается.

Результаты писать во временную папку попытки, затем atomic rename/manifest finalize. После этого короткая транзакция completed + запись delivery. При сбое между FS и DB допускаются orphan files, которые удалит cleanup; незавершённый результат нельзя объявить готовым.

После истечения lease задача помечается interrupted. Чистый рендер можно автоматически повторить максимум один раз при сохранном входе и той же версии плагина. Publication/delivery не перезапускать вслепую. Если plugin_version изменился, старую queued/interrupted задачу завершить понятной ошибкой incompatible_version и предложить новую с подтверждением; не выполнять тихо новым алгоритмом.

При SIGTERM: bot прекращает приём, worker прекращает claim, текущей работе даётся grace period, оставшаяся корректно прерывается. Docker stop_grace_period согласован с этим временем. После restart queued сохраняются, expired lease восстанавливается, delivery возобновляется по её правилам.

SQLite job queue — источник истины. asyncio.Queue допустима только как необязательный сигнал пробуждения, не как единственное хранилище работы.

## 9. Прогресс и доставка

Одна карточка задачи с кратким ID, инструментом, этапом, измеряемым процентом и «Отменить». Worker сохраняет последний прогресс в БД с throttling, bot периодически читает и редактирует карточку. Интервал примерно 1–2 секунды, обновлять только изменившийся текст. Финальный статус не терять из-за throttling. Message-not-modified безвреден; 429 обрабатывается через retry_after; массовые повторы ограничены.

Под «live progress» здесь понимается обновление известного сообщения через editMessageText/editMessageCaption, а не обязательная зависимость от отдельного streaming API. После подтверждения создаётся одна карточка статуса; сохранить chat_id/message_id в БД, чтобы обновления продолжались после restart. Не отправлять новое сообщение на каждый этап/кадр. Измеряемый fraction можно представлять компактным progress bar и процентом, например `██████░░░░ 60%`; при неизвестном fraction показывать этап без фиктивного процента/ETA. Если проценты относятся к текущему этапу, это явно подписывать, не представлять их как процент всей задачи.

Карточка показывает понятное имя инструмента и различает «Ожидает обработки», «Рендер», «Подготовка отправки», «Отправлено», «Не удалось отправить», «Отменено» и «Прервано». Результат допустимо отправлять отдельным media-сообщением, но карточка должна перейти в окончательный delivery status. При удалённой карточке допустима одна контролируемая замена с сохранением нового message_id, не бесконечное создание сообщений. Кнопка отмены и повторной отправки проверяет ACL/ownership независимо от содержимого callback.

Delivery records создаются транзакционно вместе с completed. Отдельная корутина bot process публикует и отправляет результаты с ограниченной concurrency. На network/Telegram сбое локальный рендер сохраняется, повтор отправки не пересчитывает видео.

Telegram send и SQLite commit не атомарны. При timeout после запроса сообщение могло быть отправлено. Статус uncertain должен сохранять это различие; не обещать exactly-once и не повторять бесконечно. Дать пользователю действие «Отправить результат ещё раз» с возможностью дубликата. При известном message_id можно безопасно повторять обновление известного сообщения. Blocked bot → delivery failed, без вечного retry.

Ограничения размера проверять до отправки по актуальному Bot API. При слишком большом MP4 разрешён один ограниченный повтор encode с меньшим bitrate/resolution; затем понятная ошибка. Не превращать это в бесконечный цикл. ZIP/PNG fallback для эмодзи отдавать как явно обозначенный альтернативный результат.

## 10. Хранение, лимиты и приватность

Минимальные таблицы: users, access_requests, drafts, jobs, deliveries, artifacts, emoji_sets, emoji_items/publication_steps, audit_events. Не добавлять отдельные таблицы без использования. Alembic initial migration и проверка upgrade на пустой и существующей БД. Миграции только отдельной командой, не одновременно из bot и worker.

Файлы: /data/db/app.sqlite3, /data/jobs/<job_id>/<attempt_id>/, /data/results/, /data/backups/. User filename не участвует в выборе пути. Артефакты имеют owner, sha256, размер, media_type, expires_at.

Стартовые продуктовые лимиты, конфигурируемые и НЕ выдаваемые за лимиты Telegram: 1 running глобально; до 3 незавершённых задач пользователя; до 20 queued глобально; emoji-текст до 80 символов с дополнительным ограничением плиток; crawl до 1500 символов и 45 секунд; обычная карточка до 500 символов. Плагин проверяет реальные размеры canvas и вычислительную стоимость после layout. При превышении предлагает сократить текст.

Retention: scratch удаляется после завершения/ошибки; готовые файлы и исходный текст хранятся 7 дней; служебная история без текста 30 дней. TTL настраивается. Нельзя удалять активные workspaces или файлы pending delivery. После ограниченного окна retry delivery тоже истекает. /jobs сообщает об истёкшем результате. Глобальный лимит диска и проверка свободного места перед рендером; cleanup имеет приоритет перед приёмом новой тяжёлой работы.

Не логировать bot token, исходные сообщения, файлы и full HTTP URLs с токеном. Структурированные логи: job_id, plugin_id/version, attempt, stage, duration, error_code. Детали ошибки в логах, безопасная краткая формулировка пользователю. Счётчики /status: queued/running, последний heartbeat worker, свободный диск, failed за сутки; отдельный Prometheus пока не нужен.

Бэкап SQLite делать через online backup API, не обычным cp одного .sqlite3 при работающем WAL. Для согласованной копии БД+артефактов проще остановить сервисы на время snapshot. Проверить restore на временной копии. Telegram-публикации существуют отдельно от local retention.

## 11. Особенности text_to_emoji

Рисовать всю фразу целиком, затем нарезать на 100×100 PNG/WebP. Текст не ограничен схемой «одна буква = один emoji». Сначала одна строка, ширина кратна 100 с padding, высота 100, малое число плиток. Параметры подбирать по читаемости; 100px в файле не равно 100px в чате. Проверить Cyrillic, ё, punctuation, пробелы, широкие/узкие буквы, unsupported glyph fallback. Не сжимать длинные фразы до неразборчивости.

Создавать наборы отдельно для пользователя, принадлежащие его Telegram ID. Хранить set name/ID и соответствие tile hash → custom_emoji_id. Кэш ограничен user_id, bot identity, plugin_version, font hash, settings и rendered bytes. Не делиться текстовыми артефактами между пользователями по умолчанию.

Наборы Telegram не являются приватным хранилищем: получатель может открыть набор, ссылка на набор может распространяться. Перед первым использованием показать краткое предупреждение об этом; секретные тексты не следует превращать в публикуемые emoji. Закрытый доступ к боту не делает emoji-паки закрытыми.

Publisher выполняется в bot process после рендера. Имена паков детерминированные, без пользовательского текста, с обязательным суффиксом Bot API. Операции сериализуются на набор/пользователя, шаги загрузки сохраняются после каждого успеха. После ambiguous timeout сверять фактический набор через API, чтобы не потерять уже загруженные плитки и не повторить создание. Учитывать дедупликацию одинаковых stickers: порядок композиции хранится явно по ID, не по позиции в наборе.

Проверить актуальные лимиты createNewStickerSet/addStickerToSet; на дату планирования набор custom emoji до 200 элементов, начальная загрузка до 50. При заполнении создавать следующий набор. Не заменять прежние плитки ради освобождения места: это может повлиять на старые композиции. Ввести лимит числа наборов пользователя и понятный отказ, не скрытое удаление. Удаление локальных временных файлов не удаляет Telegram-пак.

При отправке использовать custom_emoji entities или корректно экранированный HTML tg-emoji с валидным обычным emoji как fallback. При entities считать offsets/length в UTF-16. Предпочесть один централизованный builder, проверить на emoji/surrogate pairs. Исходный текст можно добавить отдельной подписью, поскольку композиция не является обычным доступным для поиска текстом.

По текущей документации direct-send custom emoji в private/group chats доступен боту при Premium у владельца; другие варианты имеют отдельные требования. Owner Premium и Premium получателя для самостоятельного использования — разные вещи. Нет надёжного универсального getMe-флага «всё разрешено»: сделать ручной capability smoke test в личном чате владельца. Если недоступно, отключить этот output или явно вернуть картинку + файлы, не заявлять успешную публикацию.

Не гарантировать цельность полосы при любом масштабе/клиенте: возможны интервалы, переносы и изменение размера emoji. Приёмка: iOS и Desktop, светлая/тёмная темы, текст рядом и сообщение только из emoji. Многострочные и анимированные композиции отложить; синхронность нескольких animated emoji не гарантировать.

## 12. Особенности space_crawl и text_card

text_card: 2–3 лицензированных шрифта с Cyrillic, цвет/фон, корректный перенос, padding, один фиксированный разумный размер. Не требовать GPU или AI. Шрифты и лицензии включены в образ, не скачиваются при каждом запросе.

space_crawl: свой звёздный фон, жёлтая типографика, перспективное преобразование и движение вверх, без заимствования музыки/киноассетов. Исходный текст сохраняется точно, автоматическое переписывание не входит в scope. Стартовые параметры 720p, 24 fps, до 45 сек; если нагрузка велика, уменьшить default и зафиксировать причину.

Кадры генерировать потоком в FFmpeg, не держать весь ролик в памяти и не писать тысячи PNG. MP4 H.264, yuv420p, faststart, без аудио. FFmpeg subprocess запускать argv-массивом, shell=False, с timeout и ограничением stderr. Проверить ffprobe: codec, dimensions, duration, отсутствие audio. Проверить глазами начало, середину и конец: текст целиком проходит кадр, кириллица читается, строки не обрезаны. Прогресс по кадрам реален; отдельный этап кодирования/финализации при необходимости.

## 13. Docker и эксплуатация

Один multi-stage Dockerfile; runtime на python:3.12-slim с зафиксированным digest после проверки. Установить FFmpeg и необходимые runtime libraries. uv/deps закрепить, `uv sync --locked` для полного проекта. В runtime нет dev dependencies, .env, tests и git credentials. Непривилегированный UID, корректные права volume, init для reaping детей, exec-form entrypoint.

Compose: migrate (one-shot), bot, worker — все один image. Сначала успешная migrate, затем bot/worker. Только bot получает BOT_TOKEN. Общий /data volume. `restart: unless-stopped`, разумные CPU/RAM limits, stop_grace_period. Никаких published ports при long polling. Не монтировать docker.sock. Не запускать второй polling instance с тем же токеном.

CLI команды: `migrate`, `bot`, `worker`, `run-job`, `healthcheck --role`, `backup`, `cleanup --dry-run`, `plugins list`, `plugins validate`. Healthcheck проверяет DB schema и свежесть heartbeat своего процесса; временная недоступность Telegram отмечается degraded и не маскируется как падение рендера. Docker unhealthy само по себе не перезапускает контейнер: фатальные ошибки должны завершать основной процесс, это описать в operations.

.env.example содержит только placeholders и описание default: BOT_TOKEN, OWNER_TELEGRAM_ID, DATA_DIR, ENABLED_PLUGINS, TZ, JOB_TIMEOUT_SECONDS, RETENTION_DAYS, MAX_QUEUE_SIZE, LOG_LEVEL. worker не должен требовать BOT_TOKEN из общей обязательной модели конфигурации. Конфигурацию валидировать для конкретной CLI role.

README: создать бота через BotFather, получить свой ID через /start, заполнить env, owner ID при первичном запуске можно получить из внешнего trusted способа или отдельной одноразовой bootstrap-команды без выдачи доступа первым пришедшим. Не делать «первый пользователь становится админом». Описать build/start/logs/stop/update/backup/restore и Premium smoke test. Для ID можно предусмотреть `/whoami`, возвращающий только собственный ID даже без доступа.

## 15. Обязательные проверки

- Неодобренный пользователь, подделанный callback и чужой job ID не дают доступ; owner не блокируется revoke.
- Дублирование confirm/update создаёт ровно одну job; старый callback не меняет новый draft.
- Два concurrent claim не забирают одну job; fencing token отклоняет старую попытку.
- Отмена queued/running, timeout и SIGTERM убивают runner и FFmpeg без сирот.
- Рестарт восстанавливает queued/interrupted и pending delivery, не рендерит completed повторно.
- Ошибка отправки отделена от ошибки обработки; uncertain не становится автоматически sent.
- Revoke перед delivery подавляет выдачу результата.
- Очистка не трогает активные/неистёкшие delivery files; path traversal отклоняется.
- Рендер Cyrillic/ё/длинных строк; пустой ввод; лимиты canvas/длины/файла.
- Emoji publication: timeout после create/add, частичный набор, одинаковые плитки, заполнение набора, повтор доставки.
- Telegram 429 уважает retry_after; blocked bot не приводит к вечному циклу.
- Alembic migration, SQLite backup/restore, запуск non-root Docker с persistent volume.

Unit tests проверяют правила, integration tests — SQLite/subprocess/media. Contract test проходит по каждому включённому плагину с fixture input. Не гнаться за процентом coverage и не писать тесты, которые только повторяют конструкторы.

Ручная Telegram-приёмка обязательна для эмодзи, переносов, Premium, картинки и MP4. Если нет BOT_TOKEN, агент полностью завершает offline-работу и честно помечает live acceptance как непроверенную. Нельзя писать «бот полностью работает» только по мокам.

## 16. Этапы реализации и критерии выхода

### A. Каркас и первый вертикальный сценарий

Создать repo skeleton, config, Docker, DB migration, owner/allowlist, private chat /start, text_card с одним стилем. Уже использовать базовый PluginSpec и явный registry, но не строить заранее универсальную платформу. Критерий: offline CLI и Docker создают валидную PNG; live бот при наличии токена отвечает владельцу и отказывает постороннему.

### B. Надёжные задачи

Добавить SQLite queue, отдельный worker, runner subprocess, статусы, progress, cancel, delivery records, восстановление, лимиты. Критерий: Docker restart/cancel/timeout/отказ delivery проходят проверки; bot остаётся отзывчивым при рендере.

Включить полноценный UX-путь из раздела 6: понятный каталог с примерами, выбор инструмента, persistent input/options, summary перед подтверждением и одна обновляемая карточка задачи. Критерий: пользователь выбирает инструмент без знания plugin_id, видит подтверждаемые текст/настройки, получает соответствующий результат, а изменения progress не засоряют чат. Проверить stale callback после изменения настроек, поиск/категории, отсутствие сохранения неизвестных команд в input и восстановление draft/status card после restart.

### C. Проверка самого рискованного сценария — emoji

Сделать статическую короткую полосу 3–6 плиток, publisher, pack persistence/reconciliation и отправку. Сначала реальный end-to-end тест владельцем, затем дополнительные стили. Критерий: выглядит приемлемо на iOS/Desktop, повтор после partial failure не теряет соответствие плиток, fallback честно обозначен. При отсутствии Premium результат этой проверки блокирует только emoji delivery, а не остальные плагины.

### D. Space crawl

Потоковый renderer + FFmpeg, настройки длины/скорости в ограниченных пределах, cancellation. Критерий: валидный MP4, текст целиком виден, нет роста RAM с числом кадров, принят Telegram как animation при live тесте.

### E. Закрытый доступ и повседневное использование

Заявки с approve/reject, история /jobs, повтор доставки, draft persistence, cleanup, backup, /status, понятные ошибки. Критерий: владелец предоставляет и отзывает доступ без ручного редактирования БД; файлы и задачи переживают restart.

Добавить недавние/избранные инструменты и проверить usability каталога на синтетическом наборе из 100 specs без 100 production-плагинов. Поиск и категория должны приводить к нужной карточке без десятков последовательных нажатий «Далее». Избранное не даёт доступа к отключённым инструментам; недавние действия не сохраняют исходный пользовательский текст.

### F. Передача и готовность к ручному деплою

CI, pinned image/deps, operations, adding-plugin с рабочим примером, архитектурные решения и checklist live acceptance. Критерий: новый разработчик поднимает bot/worker по README, добавляет простой плагин без изменений job/access core, выполняет backup/restore. CD отмечен отдельным последующим milestone.

## 17. Правила работы coding agent

После создания repo перенести краткие правила из этого раздела в AGENTS.md. Сам план сохранить как IMPLEMENTATION_PLAN.md. Вести checklist этапов и docs/decisions для существенных отклонений.

1. Сначала прочитать план целиком и проверить текущий репозиторий. Существующие изменения не перетирать.
2. Реализовывать этапы по порядку, каждый заканчивать runnable результатом и релевантными проверками.
3. Делать небольшие commits с конкретным результатом. Не переписывать всё ядро ради очередного эффекта.
4. Не считать pseudocode из плана готовой реализацией; проверить актуальные library/API contracts.
5. Новые плагины используют SDK и services. Telegram imports разрешены только в адаптерах. DB imports — только в infrastructure/bootstrap по необходимости.
6. Не оставлять TODO/pass на обязательном пути, не подменять media output заглушкой.
7. Не добавлять внешние SaaS/LLM, платные API и инфраструктурные сервисы без новой потребности.
8. Не коммитить токены, пользовательские входы, DB, data/, generated artifacts или .env.
9. При отсутствии доступа к Telegram выполнить все offline checks; явно перечислить live checks, которые остались. Не выдумывать результаты запусков.
10. Перед финалом выполнить lint/typecheck/tests, Docker build/smoke и сверить README с реальными командами.
